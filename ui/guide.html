x86sim guide

x86sim is an x86-64 CPU simulator with this web debugger. It runs programs in 16-bit real mode and 32/64-bit Linux user mode, and it emulates a whole PC that boots a stock Linux kernel on up to 255 CPUs, optionally through simulated caches, and can run KVM virtual machines on its simulated VMX.

The PC →
The simulator models architectural behavior: what each instruction does to registers, memory, and the machine. It has no pipeline, branch predictor or cycle timing. Time is virtual: each round, every running CPU executes one instruction, and a round counts as 1 ns. Runs are therefore fully reproducible.

Quick start

make                                    # build ./x86sim (just needs a C compiler)

./x86cc --ui tests/c/algo.c             # compile a C program and open it in this debugger
./x86sim -u --smp 4 --cache             # an empty 4-CPU PC: write assembly in the Editor
os/get-alpine.sh                        # download Alpine Linux into os/ (once)
./x86sim --kernel os/bzImage --initrd os/initrd.cpio   # boot it to a shell on the serial console

The web debugger listens on http://127.0.0.1:8086 (only on the local machine). Use -p N to choose another port. To boot Linux from there, press Boot OS (see Booting an OS from the debugger).

Running programs

What it can run

  • ELF object files (.o). The simulator has its own linker, so clang -target x86_64-linux-gnu -c (or i386-linux-gnu) is all you need. Several .o files are linked together. Execution starts at _start, or at main through a generated stub.
  • Static ELF executables, 32- or 64-bit, including static-PIE (for example musl -static binaries). Dynamically linked executables are refused.
  • Flat binaries, loaded as a DOS .COM program at 1000:0100 in real mode, with DOS int 21h and BIOS services.
  • Boot images, disk images and Linux kernels in PC mode (see the PC machine).

User-mode programs talk to the simulator through Linux system calls (about 45 of them, through syscall in 64-bit code and int 0x80 in 32-bit code). In the debugger the program pauses in read() until you type a line in the Console.

Compiling with x86cc

x86cc wraps clang with the right flags and links the small runtime in runtime/, which provides print_str, print_u64, print_i64, print_hex, sim_read, sim_write, memcpy and similar helpers.

./x86cc --run examples/greet.c          # compile and run
./x86cc --ui  tests/c/algo.c            # compile and open the web debugger
./x86cc --debug prog.c                  # compile and start the terminal debugger
./x86cc --run --32 prog.c               # 32-bit (i386) build
./x86cc --run --16 examples/hello16.s   # 16-bit real-mode DOS program
./x86cc --run -O2 prog.c -- arg1 arg2   # optimization level and program arguments

Panels

  • Registers highlights what the last step changed. Click a register to edit it, and click a flag to toggle it. XMM registers are shown on demand. In PC mode the header also shows the control registers and the operating mode, including VMX root or VMX guest when a hypervisor is running.

  • Memory is a hex view. The address box accepts hex numbers, symbols, registers and reg+offset.
  • CPU switcher (PC mode with several CPUs): registers, disassembly, stack and memory follow the selected CPU. There are buttons for up to 8 CPUs, and a drop-down with a running/halted summary beyond that.

Assembly editor

The Editor view (next to Disassembly) is for writing bare-metal programs and loading them onto any CPU of a PC. x86sim -u without a program starts an empty PC and opens the editor; add --smp N and --cache as you like. New machine in the editor replaces the current machine with an empty one of any size.

Writing and loading

  1. Pick an example from Examples… or write your own. Execution starts at _start, or at the first instruction.
  2. Choose the Mode (16-bit real, 32-bit protected, 64-bit long) and the Syntax (AT&T, or Intel, which adds .intel_syntax noprefix).
  3. Choose the CPU in Load on and, if you want, a physical address in at.
  4. Assemble only checks for errors, which are marked in the gutter; click one to jump to it. Load places the program and leaves the CPU ready to step in the disassembly view. Load & Run (Ctrl+Enter) starts it at once. Memory only writes the code without starting a CPU, for example as the target of your own INIT/STARTUP IPIs.

Programs are assembled by clang (set X86SIM_CLANG to use another) and linked by the simulator. The draft is kept in your browser.

Modes and memory slots

The CPU starts directly in the chosen mode, with interrupts off:

  • 16-bit real mode: CS = DS = ES = SS = address / 16. BIOS services are available.
  • 32-bit protected mode: flat segments (code 0x08, data 0x10).
  • 64-bit long mode: code segment 0x18, with the first 4 GiB identity-mapped by 2 MiB pages.

The GDT, IDTs and page tables live at 0x100000–0x10FFFF. Every CPU has a default slot, with code at the bottom and its stack at the top:

ModeDefault load address
32- and 64-bit0x200000 + cpu × 64 KiB
16-bit0x10000 + cpu × 4 KiB

A load is refused if its code and stack would overlap another loaded program; reloading the same CPU replaces its old program. A running program can still write anywhere, because on bare metal every CPU sees all of physical memory.

  • Print by writing bytes to port 0xE9; they appear in the Console.
  • cli; hlt stops a CPU. The run ends when every CPU has stopped.
  • Until a program installs its own IDT, an exception stops the run with a report such as cpu1: unhandled #UD invalid opcode at 0x210004, and halts only that CPU.

Examples

ExampleTry

The PC machine

PC mode emulates a complete machine with firmware, so real boot code and operating systems run unmodified.

Devices

  • BIOS services (HLE), with ACPI and MP tables describing the machine.
  • 8259 interrupt controllers, the 8254 timer, CMOS clock, 8042 keyboard controller.
  • A 16550 serial port, which is the terminal when you run from the command line (Ctrl+] quits).
  • VGA text mode and mode 13h (the Screen tab), PCI, and IDE disks and floppies.
  • Per-CPU local APICs (xAPIC and x2APIC), an I/O APIC, and a VT-d remapping unit.

Special I/O ports

PortUse
0xE9Debug console: a byte written here appears in the Console (Bochs/QEMU convention).
0xF4Exit: writing a byte ends the simulation with that exit code.
0xEC, 0xEDQuery the cache state of a line (see below).
0xB2Raises an SMI on the writing CPU (see SMM).

Booting an OS from the debugger

Boot OS in the toolbar replaces the machine with a fresh PC that boots an operating system. Images come from the OS library, the os/ folder next to ui/. To fill it with Alpine Linux (a 6.6 kernel plus a BusyBox userland in an initramfs), run once:

os/get-alpine.sh                        # writes os/bzImage and os/initrd.cpio
  1. Choose Linux kernel and pick the kernel (any bzImage), an initial RAM disk (or none) and the kernel command line. The default, console=ttyS0 earlyprintk=serial, sends the console to the serial port, which the Console tab shows.
  2. Or choose Disk image and pick a bootable hard disk or floppy image. Floppy-sized images go in drive A: by default. Guest writes stay in memory; the file never changes.
  3. Set the CPUs (1–255), the memory and whether to simulate caches, then press Boot.

The machine starts running at once. A Linux boot opens the Console tab: Alpine reaches its shell in about a minute and a half on 2 CPUs. Click the console and type, as in a terminal; Ctrl+C, Tab completion and the arrow keys work. Typing exit restarts the PC, which ends the run (system reset requested); Reset boots it again. A disk boot opens the Screen tab instead.

Add files… copies kernels, initrds and disk images from your computer into the library. The dialog tells kernels (the bzImage header), initrds (cpio, or gzip, xz, zstd, bzip2, lz4 or LZMA compressed) and bootable disks (the 0x55AA boot signature) apart. The debugger still works while an OS runs: Pause stops all CPUs, and the panels show the kernel's code, registers and memory. Reset boots the same OS again. The dialog remembers the last choices.

Booting Linux and disks

./x86sim --kernel os/bzImage --initrd os/initrd.cpio --append "console=ttyS0"
./x86sim --smp 8 --cache --kernel os/bzImage --initrd os/initrd.cpio
./x86sim --hda disk.img                 # boot from a hard disk image
./x86sim --fda floppy.img --boot a      # boot from a floppy
./x86sim --pc boot.o                    # your own boot sector, linked at 0x7C00

Linux boots in x2APIC mode through interrupt remapping. On 8 CPUs it takes about 45 seconds; time grows linearly with the number of running CPUs, and halted CPUs are cheap.

Multiple CPUs

--smp N gives the PC N CPUs (1–255). CPU 0 boots. The others wait for INIT and STARTUP IPIs from it, exactly as on real hardware, and the ACPI MADT and MP table list them all.

  • Each CPU has its own local APIC (APIC ID = CPU number). IPIs can be fixed, lowest-priority, NMI, INIT or STARTUP, to physical or logical destinations.
  • The CPUs run in a deterministic round robin, one instruction each per round. LOCK-prefixed instructions are therefore atomic and runs are reproducible, but plain read-modify-write sequences still race, as on real hardware.
  • CPUID reports the topology (leaves 1 and 0xB) and the caches (leaf 4).
  • The limit of 255 comes from the xAPIC architecture: APIC IDs are 8 bits, and 0xFF is the broadcast address.

Caches and MESI

--cache sends every memory access through a simulated cache hierarchy. The caches hold the real data, and memory is only updated on writeback, so a coherence bug would corrupt the guest.

CacheSizeOrganization
L1 data48 KiB per CPU12-way, 64 sets
L1 instruction32 KiB per CPU8-way, 64 sets
L23 MiB shared12-way, 4096 sets, inclusive

Lines are 64 bytes, write-back and write-allocate, with LRU replacement. The L1s stay coherent through MESI on a snooping bus:

M ModifiedE ExclusiveS SharedI Invalid
Bus eventWhenEffect
BusRdRead missA Modified copy elsewhere is written to the L2, and all copies become Shared. The reader gets Exclusive when no one else has the line.
BusRdXWrite missOther copies are flushed if Modified and invalidated. The writer gets Modified.
BusUpgrWrite hit on SharedOther copies are invalidated without a data transfer. A write hit on Exclusive becomes Modified silently.
BusWBEviction of a Modified lineThe line goes to the L2. Evicting an L2 line also invalidates the L1 copies (inclusion).

The instruction caches count as sharers, so a store invalidates stale code everywhere. CLFLUSH writes a line back and drops it; WBINVD and INVD flush everything. Video memory, the BIOS ROM and memory-mapped devices are uncached.

The Caches tab

  • Statistics: hit rates, MESI line counts per cache, and bus traffic.
  • Line lookup: enter an address to see its line's state in every cache.
  • Event log: a live log of coherence events (bus transactions and snoops).
  • Contents: a sets × ways grid of any cache, with line addresses colored by MESI state. It marks each set's most recently used line and its next victim, and flashes lines that just changed. The L2 adds an overview map of all 4096 sets.
  • Click a line to see its 64 bytes. Bytes that differ from main memory, i.e. written but not yet written back, are highlighted.
  • The view refreshes while the program runs, optionally in slow motion (10 to 100,000 instructions per frame).

Querying from a program

Write a physical address to port 0xEC as a dword, then read the dword back. It holds two bits of MESI state per cache: core first + k's L1D in bits 4k–4k+1, its L1I in bits 4k+2–4k+3, and the L2 in bits 16–17. Four cores fit in a reply; writing a byte to port 0xED selects the first core (default 0).

CPU features

Instruction set

  • All encodings decoded in 16-, 32- and 64-bit modes (VEX and EVEX are decoded for length).
  • The general-purpose integer instructions, ADX, MOVBE, CRC32.
  • x87 with 80-bit, correctly rounded arithmetic; MMX; SSE through SSE4.2; AES-NI, PCLMULQDQ, SHA.

Anything not implemented stops with a clear instruction not implemented yet: … message instead of misbehaving.

System architecture

Real, protected, long and virtual-8086 modes. Paging (32-bit, PAE, 4- and 5-level) with PCIDs, SMEP/SMAP, and protection keys. Hardware task switching, SYSCALL/SYSENTER, XSAVE, FSGSBASE, UMIP, and CET (shadow stacks and indirect-branch tracking). Exceptions are precise.

Performance counters

Architectural perfmon version 4: 3 fixed and 8 general 48-bit counters, global control and status, RDPMC, and overflow interrupts (as a vector or an NMI). Events: instructions, cycles (one per instruction), branches, and, with --cache, L1D/L1I/L2 misses and cross-core transfers of Modified lines.

Transactional memory (TSX RTM)

XBEGIN, XEND, XABORT, XTEST in PC mode. Stores are buffered per cache line until XEND commits. A conflicting access by another CPU, an exception, an interrupt, capacity (512 lines), nesting past 7 levels, or I/O, CPUID and system instructions abort the transaction, with the architectural status in EAX.

System management mode

SMIs come from port 0xB2 or from APIC IPIs with delivery mode SMI. The CPU saves its state in the Intel 64 save-state map at SMBASE + 0xFE00 and enters SMM at SMBASE + 0x8000. RSM supports SMBASE relocation and the auto-HALT restart; SMRRs hide SMRAM outside SMM. The firmware has no SMI handler, so a program that raises SMIs brings its own.

x2APIC and VT-d interrupt remapping

The local APICs support x2APIC mode (MSR interface, 32-bit IDs, cluster logical mode, self IPI). A VT-d remapping unit, described by an ACPI DMAR table, provides interrupt remapping with x2APIC destinations and queued invalidation. DMA translation is accepted but not applied, since no device does bus-master DMA.

Virtualization (VMX)

Intel VT-x in PC mode, complete enough for Linux's KVM to run guests with all of its hardware features enabled. CPUID reports VMX, and a hypervisor uses it as on real hardware: set CR4.VMXE, lock IA32_FEATURE_CONTROL, then VMXON, set up a VMCS with VMWRITE, and VMLAUNCH.

  • Instructions: VMXON, VMXOFF, VMCLEAR, VMPTRLD, VMPTRST, VMREAD, VMWRITE, VMLAUNCH, VMRESUME, VMCALL, INVEPT, INVVPID and VMFUNC, with the architectural success and failure results and error numbers.
  • VM entry performs the control, host-state and guest-state checks, loads the guest, and handles MSR-load lists and event injection. VM exits record the reason, qualification and interrupt information, then load the host.
  • Exits for exceptions, interrupts, NMIs, interrupt and NMI windows, triple faults, INIT, CPUID, HLT, I/O, MSRs, control registers, and the other instructions VMX can intercept.
  • Memory: EPT (4-level, 2 MiB and 1 GiB pages, accessed/dirty flags, execute-only pages), VPID, unrestricted guests, page-modification logging, and EPTP switching.
  • Timing: TSC offsetting and scaling, the VMX-preemption timer, and pause-loop exiting.
  • APIC virtualization: TPR shadow, the APIC-access page, x2APIC-mode virtualization, virtual-interrupt delivery, and posted interrupts.
  • Nesting support: VMCS shadowing, and VMWRITE to any field.

While a hypervisor runs, the debugger header shows VMX root or VMX guest. The Linux test suite boots Alpine's linux-virt kernel, loads kvm-intel.ko (it reports APICv, PML, the preemption timer and shadow VMCSs enabled), and runs a KVM guest that takes timer and IPI interrupts.

Not modeled: SMM dual-monitor treatment, EPT-violation #VE, sub-page permissions, mode-based execute control and IPI virtualization. The capability MSRs report them as absent, so software doesn't try to use them.

Limits

  • Not yet implemented: AVX, AVX2, FMA and AVX-512 execution, BMI1/2, and SGX.
  • No microarchitecture: no pipeline, branch prediction or cycle-accurate timing. The LBR MSRs hold values but record nothing.
  • User mode supports about 45 Linux system calls and static executables only.
  • At most 255 CPUs (the xAPIC limit).
